# Local Arcade 발표 대본

권장 시간은 18~22분입니다. 프로젝트의 기획 배경을 먼저 설명한 뒤, 크레딧 생명주기와 트래픽·통신·동시성·트랜잭션을 깊게 설명합니다.

## 1. 표지

Local Arcade는 같은 LAN에 있는 최대 6명이 참여 코드만으로 접속해 게임과 채팅, AI 학습 퀴즈를 함께 사용하는 풀스택 플랫폼입니다. 개인 프로젝트로 기획, UI, 서버, DB, AI 연동을 모두 구현했습니다.

## 2. 목차

발표는 프로젝트, 아키텍처, 엔지니어링, 주요 기능, 검증의 다섯 부분으로 진행합니다. 핵심은 여러 사용자의 요청이 겹쳐도 공유 상태와 크레딧을 일관되게 유지한 방식입니다.

## 3. 프로젝트 소개

게임을 여러 개 만드는 것 자체보다, 서로 다른 게임이 공통 플레이어와 크레딧을 공유할 때 상태를 어떻게 안전하게 유지할지를 핵심 목표로 잡았습니다.

## 4. 기획 배경

게임은 짧은 시간에 참가, 크레딧 차감, 결과 판정과 정산이 반복됩니다. 이 과정에서 여러 사용자의 요청이 같은 시점에 도착해도 중복 차감이나 서로 다른 결과가 발생하지 않아야 합니다. 이를 검증하기 위해 레이싱·야추·행맨·마피아가 하나의 플레이어와 크레딧을 공유하고 서버가 최종 결과를 판정하도록 구성했습니다. 크레딧은 서비스 내부에서만 사용하는 게임 점수입니다.

## 5. 기술 스택

React와 TypeScript가 입력과 화면 표현을 담당하고, Spring Boot가 게임 판정과 크레딧 정산을 담당합니다. MySQL에는 플레이어와 AI 문제를 저장하며, OpenAI Responses API는 로컬 위키를 근거로 문제를 생성합니다.

## 6. 시스템 구조

브라우저는 1초마다 상태를 동기화합니다. 조회 요청은 바로 처리하지만 게임 상태를 바꾸는 명령은 큐를 통해 순서대로 처리합니다. DB 변경은 트랜잭션으로 묶었습니다.

## 7. 크레딧 생명주기

참가 요청은 허용 금액, 잔액, 중복 참가를 검증한 뒤 크레딧을 차감합니다. 게임 진행 상태에는 참가자와 pot을 기록하고, 서버가 결과를 한 번만 생성한 뒤 우승자 크레딧을 저장합니다. DB 변경은 트랜잭션으로 묶지만 턴과 pot 같은 메모리 상태는 롤백되지 않으므로 명령 큐와 synchronized를 함께 사용했습니다.

## 8. 사용자 흐름

서버가 발급한 코드로 입장하고, 게임 참가부터 결과 정산까지 하나의 세션에서 진행됩니다. 모든 게임의 결과가 공통 크레딧과 랭킹에 반영됩니다.

## 9. 야추

야추는 턴, 굴림 횟수, HOLD, 점수표가 동시에 얽히므로 서버 상태 검증을 보여주기 좋은 기능입니다. 화면의 주사위 값까지 서버 값과 비교한 뒤에만 점수를 확정합니다.

## 10. 레이싱

각 브라우저에서 랜덤 결과를 만들지 않습니다. 서버가 한 번만 순위를 만들고 raceId와 함께 공유하며, 클라이언트는 그 결과를 애니메이션으로 표현합니다.

## 11. AI 퀴즈 개요

AI를 단순 호출하지 않고 위키 발췌, 구조화 출력, 서버 검증, 저장과 재사용을 하나의 파이프라인으로 만들었습니다.

## 12. 게임 콘텐츠 확장

마피아와 행맨도 같은 서버 중심 상태 관리 원칙을 사용합니다. 마피아 채팅은 공용 채팅과 별개이며 낮에는 생존자가 대화하고 밤에는 마피아 역할만 접근하도록 게임 단계와 권한에 종속됩니다. 여러 게임은 단순 수량이 아니라 서로 다른 상태 전이와 동시 요청을 검증하는 사례입니다.

## 13. 캐릭터 컨트롤

requestAnimationFrame 호출 횟수가 아니라 프레임 간 시간 차이 dt로 이동량과 중력을 계산해 환경에 따른 속도 차이를 줄였습니다.

## 14. 채팅과 관리자

공용 채팅은 현재 선택한 게임과 무관하게 모든 접속자가 사용하는 서비스 채팅이며 최근 80개 메시지를 관리합니다. 마피아의 낮/밤 채팅은 별도 게임 상태로 관리합니다. 공용 크레딧과 랭킹이 게임들을 하나의 플랫폼으로 연결하고, 관리자 변경 역시 허용 단위와 인증 코드를 서버에서 검증합니다.

## 15. 프로모션 광고

외부 프로모션을 서비스 안에 연결하기 위해 상단 배너와 세션당 한 번 표시되는 모달을 추가했습니다. 이미지는 로컬 자산으로 관리하고 원본 비율을 유지했으며, 클릭 시 Instagram 원본 게시물로 이동합니다. 슬라이드 사진은 실제 모달이 보이도록 모니터 중심으로 크롭했습니다.

## 16. 서버 중심 상태 관리

공유 상태 변경은 명령 큐와 synchronized로 순서를 제어하고, DB 변경은 트랜잭션을 적용했습니다. 클라이언트 값은 최종 판단 근거로 신뢰하지 않습니다.

## 17. 테스트

현재 야추 점수 규칙과 마피아 상태 흐름을 JUnit으로 검증합니다. 향후에는 동시성 및 Controller 통합 테스트를 추가할 계획입니다.

## 18. 회고

가장 큰 학습은 정상 실행보다 동시 요청과 중간 실패 시 상태를 먼저 설계해야 한다는 점입니다.

## 19. 요청 트래픽 모델

최대 6명이 기본 상태와 소셜 상태를 각각 초당 한 번 조회하므로 기본 약 12개의 읽기 요청이 매초 발생합니다. 이는 계산값이며 실제 부하 테스트 수치는 아닙니다. 모든 요청을 큐에 넣지 않고 상태 변경 명령만 큐로 통제했습니다.

## 20. 통신 구조

현재 구현은 WebSocket이 아니라 TCP/IP 위의 HTTP REST와 1초 폴링입니다. 최대 6명 환경에서는 단순한 복구와 구현 비용을 선택했습니다. 확장 시에는 WebSocket으로 상태 변경 이벤트만 푸시하고, 게임 Room별 채널과 Redis Pub/Sub로 서버 간 이벤트를 공유할 계획입니다. 재연결, 메시지 순서, 중복 처리와 backpressure는 함께 해결해야 할 운영 과제입니다.

## 21. 명령 큐

단일 Worker가 변경 명령의 실행 순서를 보장합니다. 큐 크기를 128개로 제한해 무한 적재를 막고, 포화되면 빠르게 실패시켜 재시도를 안내합니다. 소규모 LAN 환경에서 처리량보다 일관성을 선택한 설계입니다.

## 22. 동시 요청 처리

A와 B가 거의 동시에 마지막 크레딧으로 참가해도 큐에서는 A 요청을 완료한 뒤 B 요청을 실행합니다. B는 A 처리 후의 최신 잔액으로 다시 검증되므로 잔액 부족 응답을 받습니다. 단일 큐는 병목이지만 현재 규모에서는 설명 가능한 상태를 우선한 선택이며, 확장 시 게임 Room별 큐로 분리합니다.

## 23. 최대 6명 동시 요청 검증

설계 설명에 그치지 않고 실제 목표 범위인 6명으로 API 동시 요청 테스트를 수행했습니다. 6명 입장과 야추 참가가 모두 성공했고 각 사용자의 참가비는 한 번만 차감됐습니다. 동일 사용자의 중복 참가 요청 5건은 모두 거절됐으며 상태 조회 60건은 실패 없이 처리됐습니다. 평균 응답 시간은 30.37ms, p95는 79.85ms, 최대는 107.17ms였습니다. 대규모 부하 성능 수치가 아니라 최대 6명 환경의 동시성과 데이터 일관성을 검증한 결과입니다.

## 24. Python 자동 검증 스크립트

테스트 결과를 반복해서 재현할 수 있도록 Python 표준 라이브러리만 사용하는 실행 스크립트를 작성했습니다. ThreadPoolExecutor로 6개의 참가 요청을 병렬 전송하고, 응답 성공 수와 로비 인원, 테스트 전후 크레딧을 비교합니다. 같은 토큰으로 중복 참가 요청 5건도 전송하며 상태 조회 응답 시간과 성공률을 집계한 뒤 Markdown 보고서로 자동 저장합니다.

## 25. 트랜잭션 경계

참가비 차감, 점수 확정, 우승 보상처럼 하나의 게임 사건으로 인식되는 DB 변경을 메서드 단위 트랜잭션으로 묶었습니다. 예외가 발생하면 일부 데이터만 저장되는 것을 막습니다.

중요한 한계도 있습니다. Java 메모리에 있는 게임 상태는 DB 트랜잭션의 롤백 대상이 아닙니다. 서버를 여러 대로 확장하려면 상태를 Redis나 DB로 옮기고 별도의 동시성 제어가 필요합니다.

## 26. 실패 시나리오

동시 참가, 중복 클릭, 정산 중 DB 오류, 큐 포화 네 가지 상황을 기준으로 설계를 검토했습니다. 성공 경로뿐 아니라 실패 후에도 크레딧과 게임 상태가 설명 가능한지를 중요하게 봤습니다.

## 27. 확장 전략

현재는 최대 6명이라는 요구사항에 맞춰 단일 서버와 폴링을 선택했습니다. 규모가 커지면 WebSocket, Redis, 낙관적 락, 게임 Room별 큐 분리 순서로 확장할 수 있습니다.

## 28. AI 문제 출제

Markdown 중 출제 가능한 문서 세 개를 고르고, 해당 발췌문만 근거로 사용하도록 프롬프트를 제한합니다. 최근 20개 문제 이력도 전달해 반복을 줄입니다. 게임 보상과 연결했기 때문에 AI 기능이 별도 데모가 아니라 플랫폼의 실제 콘텐츠가 됩니다.

## 29. AI 검증

JSON Schema로 필수 필드와 선택지 개수를 강제한 뒤, 서버가 정답 범위와 출처 경로를 다시 검사합니다. 생성 실패 시 최대 세 번 재시도합니다.

## 30. AI 저장과 재사용

문제, 선택지, 정답, 설명, 출처를 함께 저장합니다. 정규화한 문장 signature에는 unique 제약을 두어 중복을 막습니다. 관리자가 생성을 끄거나 API를 사용할 수 없는 상황에는 저장 문제를 다시 출제해 서비스 연속성과 비용을 함께 관리합니다.

## 31. 결과

이 프로젝트는 여러 미니게임을 모은 결과물이 아니라, 반복 요청과 공유 상태, 트랜잭션, AI 출력의 신뢰성을 하나의 서비스 안에서 실험하고 구현한 프로젝트입니다.

## 예상 질문 핵심 답변

- 대규모 트래픽을 처리했나요?  
  실제 대상은 LAN 최대 6명입니다. 대규모 처리 경험이라고 표현하지 않고, 반복 폴링과 동시 변경 요청을 제한된 큐와 서버 검증으로 통제한 설계 경험이라고 설명합니다.

- 단일 큐는 병목 아닌가요?  
  맞습니다. 현재 규모에서는 일관성을 얻는 단순한 선택입니다. 확장 시 게임 Room별 큐 파티셔닝과 Redis 기반 분산 상태로 전환합니다.

- @Transactional이면 인메모리 상태도 롤백되나요?  
  아닙니다. JPA로 관리되는 DB 변경만 롤백됩니다. 이 한계를 인지하고 있으며 분산 환경에서는 게임 상태도 외부 저장소에 두어야 합니다.

- AI가 틀린 설명을 저장할 수 있지 않나요?  
  가능성을 완전히 없앨 수는 없습니다. 현재는 제공 문서만 근거로 제한하고, 출력 구조와 출처를 검증합니다. 다음 단계는 관리자 검수 상태와 승인 워크플로를 추가하는 것입니다.
